# 关卡切换方案（研究 + 三案对比）

> 结论先行：**换场没有技术债，只有设计债。** 实测换场 1~2ms，而当前「过关→下一间」只有 0.20s 推镜、
> 零音效、零确认拍，玩家拿到"解开了"的正反馈不到 1 帧就被切走。三案的核心分歧不是特效，
> 而是**要不要给"解开"这件事留时间**。

## 0. 先看事实：换场到底多贵

探针 `_reference/tools/probe_gate.gd`，`--headless --fixed-fps 60`，Godot 4.7.2。

| 项目 | 实测 |
|---|---|
| 首关冷加载（含首次瓦片集/着色器） | 210 ms |
| 后续房间冷加载 | 0.9 ~ 4.1 ms |
| 热加载（资源已缓存） | 1.3 ~ 9.1 ms |
| `instantiate()` 单个房间 | 0.5 ~ 0.7 ms |
| 5 间房全量预载 | 35.9 ms |
| 玩家场景实例化 ×5 | 0.17 ms |

**一帧 16.67ms，换场连一帧都占不满。** 这意味着：

1. 「过渡动画在藏加载」这个理由在这里不成立——没有加载可藏；
2. 任何过渡时长都是纯设计决策，不存在"必须等多久"的技术下限；
3. 唯一可能拖慢的是 `session.gd` 里 `get_viewport().get_texture().get_image()` 的 GPU 回读
   （1280×704 全屏 readback），这条 **headless 测不到**，属 [待验证]。

## 1. 现在有四个转换时刻，只有一个被设计过

| 时刻 | 现状 | 时长 | 问题 |
|---|---|---|---|
| 菜单 → 游戏 | `change_scene_to_node` 硬切 | **0** | 没有过渡，画面直接跳 |
| 房间 → 同章下一间 | 抓帧 + 方向推镜 + 相机位移 | 0.20s | **无确认拍、无音效**；`$UI/Win` 面板被同帧隐藏，≈0 帧可见 |
| 第 5 间 → 章末 | `result` 浮层卡片 | 即时 | 有卡片，但无进入动画，硬弹 |
| 死亡 → 重生 | 角色 alpha 淡到 0.18 后瞬移 | **1.3s** | 高频动作，纯等待；且无全屏反馈 |

### 1.1 最刺眼的一条：过关没有"解开"的瞬间

`room_controller.complete()` 设 `won = true`、显示 `$UI/Win`、冻结玩家与虚影；
`session._process` **下一帧**就 `old_panel.hide()` 并 `launch(following)`。
所以那行"通关"面板最多存在 1 帧（16ms），玩家看到的是：**按住最后一个机关 → 画面立刻横移 → 你已经在新房间了。**

这直接踩中两条已被反复验证的设计教训：

- **Chapliboy（KCPS）**：玩家常常"碰巧"过关而不知道自己做对了什么。他的解法不是加过关界面，
  而是**给退出加摩擦**——过关后关卡重置，玩家得主动离开。核心洞察是：
  *"有摩擦去验证解法，比有摩擦去离开更容易让玩家学到东西。"*
- **Curvy 的复盘**：通关弹窗盖住成品画面被玩家一致批为反高潮，
  *"奖励必须先被看见、被品味，然后才被处理"*。

你的房间只有一屏，**解法本身就是全部画面**。切走等于撕掉答案。

### 1.2 第二个刺眼：全项目 0 个 `AudioStreamPlayer`

`grep AudioStreamPlayer` 在 `_reference/` 之外**零命中**。而研究里最反复的一句是：
*"糟糕的音频交接比画面更早暴露这是加载"*、*"玩家能原谅粗糙的音效，不能原谅静音。"*
没有声音时，推镜会被读成"卡了一下"，而不是"我走进下一间房"。

### 1.3 一个不能动的数：死亡 1.3s

`death_duration = 1.3` 看着像表现参数，其实**同时是玩法参数**——虚影播完轨迹后的"尸体"
会在场上保持实体 1.3s，可以当垫脚石站（`test_echo_lifetime.gd`、`test_echo_environment.gd`
都在断言这条）。砍它 = 砍关卡的可解窗口。
真要缩短，必须先把「尸体存活时长」从 `death_duration` 拆成独立常量，那是另一件事。

## 2. 研究到的五个可借用的模式

| 模式 | 出处 | 内核 | 对本项目的可用性 |
|---|---|---|---|
| **门 = 阈值** | 空洞骑士（门切换配黑屏间隙，按 I/II/III 级场景分层） | 换场不是"消失+出现"，是"穿过一个界" | ★★★ 已有出口，只差让它"有厚度" |
| **电梯/气闸** | Portal 结尾电梯、Half-Life 的 airlock | 用固定空间买节奏，不买加载 | ★★ 需要新场景，成本高 |
| **方向即空间** | Celeste 房间转场、TapTap 转场分层理论 | 横向滑动=并列，纵向=楼层，黑场=时空不连续 | ★★★ 现在的推镜方向已经做对了 |
| **门厅效应** | gamedeveloper《What Lies Beyond: Doorways》 | 走过门会让大脑重置情境记忆 | ★★★ 但**重置前必须给一拍确认** |
| **时间而非空间** | Braid / P.B. Winterbottom 类回溯 | 用"时间"解释位移 | ★★ 与你的虚影设定天然契合，但语义风险高 |

时长参考（三家说法基本一致，取交集）：

- 场景切换 **200~300ms** 是"被识别为有意设计"的下限；**<150ms 等于没发生**；**>500ms 开始像在等**。
- 更细的分层：同级 UI 0.2~0.4s / 浮层 0.3~0.6s / **场景级 0.8~1.5s+**。
- 你在 0.20s——正好压在"被识别"的下限上，且没有任何声音兜底，所以读起来像硬切。

## 3. 三套方案

前提假设（**不对请直接否掉，会改方向**）：

- 单间房 1~3 分钟，一章 8~15 分钟；玩家单间死亡率高（10~30 次）[假设]
- 设计支柱：一屏一题 / 过去可重演 / 安静克制 / 试错便宜 [假设]

### 方案 A：修边（不动结构，只补反馈）

把四个时刻的毛边各修一刀，不加新场景、不加新美术。

| 改动 | 数值 | 依据 |
|---|---|---|
| 过关插入确认拍 | 定格 **0.30s**，角色/机关/虚影全停，只让房间编号淡入 | ≥0.3s 才够"看见自己解开了" |
| 推镜 | 0.20 → **0.28s**，`SINE/EASE_IN_OUT` → **`CUBIC/EASE_OUT`** | 尾巴收得干脆，头部不拖 |
| 视差 | 背景层移动 **0.6×**，前景 1.0× | 单屏房间唯一能廉价的"厚度" |
| 菜单 → 游戏 | 0.25s 从背景色淡入 | 现在 0s，是 bug 级体验 |
| 章末卡片 | 0.25s 缩放 0.96→1.0 + 淡入 | 与浮层层级匹配 |
| 音效 | 过关一声、推镜一声（开门/风） | 无音频时这是收益最高的一项 |

- **成本**：约 1 天，改 `session.gd` + `room_controller.gd` + 一个 `AudioManager`
- **收益**：去掉"廉价感"，过关终于有"我赢了"的一拍
- **代价**：房间之间仍然是"跳过去的"，没有空间感

### 方案 B：门口停一拍（把出口做成阈值）— 推荐

在 A 的基础上，把出口从"踩到即切"改成两段式**进入 → 穿过**。

```
玩家进入出口框
  ├─ 0.15s  门在身后落下（复用 puzzle_door 的关门 tween），房间整体压暗到 0.75
  ├─ 0.30s  停一拍：画面静止，只留角色与门；一声门闩 + 一次低频呼吸
  ├─ 0.25s  推镜（同 A 的视差与缓动），新房间从同一侧推入
  └─ 0.15s  新房间 modulate 0.85 → 1.0「点亮」
```

- **成本**：2~3 天（`level_exit.gd` 加状态机、新增 `transition.gd`、`session.gd` 接线、2 条音效）
- **收益**：空间连续性最强；"停一拍"同时承担**确认拍**和**节奏呼吸**；
  门落下把"你完成了这间房"讲成动作而不是文字
- **风险**：门在身后关 = 不可回头，和"虚影能重演过去"有轻微语义冲突。
  处理办法是在叙事上区分——**不是"回不去"，是"这间房已经结束了"**
- **风险**：0.85s 总时长比现在多 0.65s。按每章 5 间算，一章只多 3 秒；但**死亡重试不走这条路**，
  所以高频路径不受影响

### 方案 C：回声转场（用时间解释位移）

```
0.15s 定格去色 → 0.35s 画面倒带（横向撕裂 + 反向抖动 + 磁带咔哒）
→ 0.40s 新房间从琥珀色显影回正常色
```

- **成本**：4~6 天（去色/色偏 shader 或三帧预渲染 + 专属音效），且**必须先有音频基础**
- **收益**：唯一性最强，把"你刚做的事会被记住"变成每次过关的仪式
- **风险（我判断这条会咬人）**：**语义污染**。玩家看到倒带会立刻试探"我能不能回到过去"，
  而机制上不能。且「安静克制」这条支柱会把"倒带撕裂"读成炫技
- **我的立场**：**这一版不做**。等到第二章、音效体系成型后再评估，否则是一个没有声音的倒带，
  剩下的只有"画面怪"

## 4. 对比与推荐

| | A 修边 | B 门槛 | C 回声 |
|---|---|---|---|
| 过关确认拍 | 0.30s 文字 | **0.30s 动作 + 声音** | 0.15s |
| 房间切换总时长 | 0.58s | **0.85s** | 0.90s |
| 空间连续性 | 弱（滑动） | **强（穿门）** | 弱（时间） |
| 新增美术 | 0 | 0（瓦片拼门口） | shader/序列帧 |
| 改动文件 | 2 | 3 + 1 新 | 5 + shader |
| 工期 | 1 天 | 2~3 天 | 4~6 天 |
| 主要风险 | 仍是"跳过去" | 不可回头的叙事冲突 | 语义污染 |

**推荐：A 先做，B 在第一章收尾前做，C 推迟。**

理由是一条因果链而不是审美偏好：你的支柱是「安静克制」+「试错便宜」，这两条同时把转场
往**短、轻、有呼吸**推；C 的倒带是"长、响、有仪式"，与支柱反向。B 的门口停一拍是唯一
**同时**服务两条支柱的做法——它把确认拍藏进一个动作里，既不弹窗（克制），又不多花一次点击（便宜）。

## 5. 验收口径（做之前先定死，否则没法判断好坏）

| 信号 | 失败的样子 | 通过线 |
|---|---|---|
| 玩家知道刚解开了 | 问"我刚才做了什么"、立刻按 R 复看 | 过关后 3 秒内无 R 输入 |
| 换场不像卡顿 | "卡了一下"的口头反馈 | 5 人试玩 0 例 |
| 不可回头的冲突 | 玩家在门口反复左右试探 | 出口前停留 <1.5s |
| 节奏 | 一章总时长明显变长 | 单章增幅 <5% |

## 6. 还没定的两件事

1. **死亡 1.3s 要不要动**：它被虚影机制占用（尸体当垫脚石站 1.3s），不能直接砍。
   要动得先把「尸体存活」拆成独立常量，属另一项工作。**本方案暂不含此项。**
2. **`get_image()` 全屏回读的真实开销**：headless 测不到，需要在带窗口的模式下加一帧计时。
   如果实测 >4ms，推镜方案要换成"先播旧帧再切场"，而不是"切场同时抓帧"。

# 方案 D：方向即空间（Celeste 式）

> 选定方向后追加。前面的 A/B/C 讨论的是「停多久」，D 讨论的是「往哪边推」。
> 两者可以叠加，不冲突。

## 7.1 结论先说：这条已经做了一半，而且做得是对的

`frontend/glue/session.gd` 里已经有两段东西：

- `exit_direction()`：算出出口在视口的哪一侧，返回 `LEFT / RIGHT / UP / DOWN`
- `slide_into_room()`：抓上一帧、把它朝反方向推出，同时把相机 offset 拉回原位

也就是说「往哪推」的判定和「怎么推」的实现都在。缺的不是代码，是**规则**——
没人定义过什么时候该滑、什么时候不该滑，也没有任何测试保护「滑的方向和玩家出现的位置一致」。

实测盘点了五间房（`--headless`，读 `Exit` 与 `RespawnPoint` 的世界坐标）：

| 房间 | 出口位置 | 出口相对视口中心 | 推断方向 | 出生点 |
|---|---|---|---|---|
| tutorial_relay | (1088, 416) | 右 | `RIGHT` | (420, 596) 偏左 |
| tutorial_steps | (1088, 352) | 右 | `RIGHT` | (248, 596) 左 |
| chapter_01_room_03 | (1184, 416) | 右 | `RIGHT` | (56, 596) 左缘 |
| chapter_01_room_04 | (1184, 448) | 右 | `RIGHT` | (56, 596) 左缘 |
| chapter_01_room_05 | (1184, 416) | 右 | `RIGHT` | (56, 596) 左缘 |

**五间房全部「从右出、从左进」，横滑语义是自洽的。** 这很关键——效果已经成立，
只是没人验证过，属于「碰巧对了」。

两个必须记下来的坑：

1. **`chapter_01_room_04` 场景里 `Player.position` 曾写成 `(1040, 854)`**——y=854 在 704 高的视口下方、
   也超过 `kill_y = 750`，看起来像「开局摔死」。实测不是：`_ready` 会用 `RespawnPoint`（56, 596）
   覆盖它，90 帧内 `is_dead` 始终为 false。**已于 2026-11-21 改回 `(56, 596)`**，
   否则这个值迟早会误导人。
2. **纵滑从未触发过**。`exit_direction()` 里 `UP/DOWN` 那两个分支是死代码，
   因为没有任何一关的出口在上下半区。

## 7.2 三条规则（这是 D 的全部内容）

| 规则 | 触发条件 | 转场 | 语义 | 时长 |
|---|---|---|---|---|
| R1 横滑 | 出口在左/右半区，且下一关同章相邻 | 旧图向出口对侧移出，新房间从出口同侧推入 | 并列的房间 | 0.24s |
| R2 纵滑 | 出口在上/下半区 | 同上，但走 y 轴 | 上一层 / 下一层 | 0.24s |
| R3 黑场 | 跨章、重试、选关跳转、非相邻 | 0.10s 黑出 + 0.10s 黑入 | 空间上没有关系 | 0.20s |
| R4 不转场 | 死亡复活 | 原地淡出，不加遮罩 | 同一空间，只是时间重置 | 现有 1.3s |

R3 的判定要在 `transition_plan()` 里显式写，不能靠「走到 else 分支」：
`to_index != from_index + 1` 一律 cut，即使它们同章。

## 7.3 核心契约：出口边必须等于对侧的进入边

这条是整套效果成立的地基：

```
exit_edge(i) == opposite(enter_edge(i + 1))
```

从右边出去，就必须从左边进来。一旦不成立，玩家会看到「从右边走出、却从中间冒出来」，
这不会被读成「转场不好看」，会被读成 **bug**。

现在的五间房满足这条（右出 / 左进），但**没有任何东西保证以后也满足**。
队友加房间时随手把出生点摆中间，效果就破了，而且没人会立刻发现——因为滑动本身还在。

所以必须落成断言，进 `frontend/tests/`：

```gdscript
# test_transition_space.gd（新增）
# 1. 对每对相邻且都有场景的房间：exit_edge(i) == opposite(enter_edge(i+1))
# 2. 第一间房必须有 enter_edge（否则从菜单进去不知道从哪边站）
# 3. 跨章连接一律 cut（不能横滑）
# 4. 重试同一间房一律 cut
# 5. 滑动时长 0.24s、黑场 0.10+0.10
```

`enter_edge` 的推断规则（不需要手填）：
`RespawnPoint.x < 房间宽/2` → 左；`y < 房间高/2` → 上；两者都接近中心则报错，要求手填。

## 7.4 实际改了什么（2026-11-21 已落地）

| 文件 | 改动 |
|---|---|
| `frontend/glue/session.gd` | 新增 `transition_kind()` / `transition_plan()` / `slide_axis()`；`launch()` 拆成 `swap_room()`（同步换）与 `cut_into_room()`（0.10s 黑出→换→0.10s 黑入）；滑动 0.20→**0.24**；滑动期间调 `lock_player(0.24)` |
| `frontend/db/catalog.gd` | 注释里写明可选 `link` 字段（`"h"` / `"v"` / `"cut"`）；`.tres` 不需要改结构，Dictionary 本就自由 |
| `scripts/player.gd` | 新增 `input_locked` + `lock_input(seconds)`；锁期间水平轴归零、禁跳、禁 E 自杀；**到期自动解除**，不依赖调用方再调一次 |
| `frontend/tests/test_transition_space.gd` | 新增 32 条断言，见 7.3 |
| `scenes/levels/chapter_01_room_04.tscn` | `Player.position` 从废弃的 `(1040, 854)` 改回 `(56, 596)` |

三个设计决定，都不是随意选的：

**① 只有「刚打完、顺序进下一间」才滑动。** `launch()` 新增 `auto_advance` 参数，只有
`_process` 自动推进那条路传 `true`。选关、重试、章节跳转、继续游戏一律切黑——
它们没有「空间连续」可言，硬套滑动会变成「从右边走出去却从中间冒出来」。

**② 黑场先把画面对黑，再换场景。** 换完再淡入等于只有一半；正确顺序是
黑出 0.10 → `change_scene_to_node` → 黑入 0.10。实现上把换场景挂在 tween 的
`tween_callback` 里，`switching = true` 从黑出第一帧就生效，挡住中途输入。

**③ 输入锁自己会过期。** 给玩家 `lock_input(秒)` 而不是一个布尔开关：
布尔开关一旦前端中途被释放，玩家就永久不能动。现在锁的计时在 `_physics_process` 里递减，
到期自动解锁，最坏情况只是多锁 0.24s。

**为什么必须锁**：滑入时玩家其实已经站在新房间里了（只是被旧截图盖着）。
如果这时玩家按着左，0.24s 能跑 65px，滑完露出画面时人会偏出出生点——
「方向即空间」立刻破功。


## 7.5 性能：回读是全屏的，实测 3.37ms

上一轮把 `get_image()` 的开销列为待验证。现在在**带窗口**模式下实测了
（`_reference/tools/probe_capture.gd`，1280×704，40 次采样）：

```
mean 3.37ms   p50 3.27ms   p95 4.60ms   max 4.72ms
```

一帧 16.67ms，回读占 20~28%。触发切场的那一帧会多花 3.4ms，**可能掉 1 帧**。
但那一帧旧截图正好盖满全屏，肉眼看不出，所以可以接受。

如果以后要求零掉帧，替代方案是「双场景并排」：不截图，把旧场景留在树里、
整体平移一个房间宽度，新场景同向推入。好处是 0ms 回读、且是实时的；
代价是要绕过 `change_scene_to_node()`（它会 free 旧场景）、手动管两个相机和
两套物理的 `process_mode`。**这一版不做**，3.4ms 不值得换这个复杂度。

## 7.6 出口贴不贴边，是效果强弱的开关

现在出口方块在 x=1184（宽 64），右边界是 1280，**离边还有 96px**。
玩家是「踩到方块」就切，不是「走出边缘」就切。这带来一个观感差：
旧截图里玩家站在房间内侧、离右边界还有段距离，然后画面就开始横移了。

| 做法 | 观感 | 代价 |
|---|---|---|
| 保持现状（踩方块即切） | 方向对，但「走出去」的感觉弱 | 0 |
| 出口右移贴边（x=1216，宽 64 到边界） | 玩家走到房间尽头才切，接近 Celeste | 改 5 个场景的 Exit 坐标 |
| 出口改成「越界触发」 | 最像 Celeste，无缝 | 要改 `level_exit.gd` 的判定，且门在后面视觉上没了 |

## 7.7 这套方案的代价（诚实版）

1. **玩家会开始期待方向一致性**。一旦学会「往右走 = 右边的房间」，任何一次不遵守都会被当成 bug。
   这条语法越有用，违反它的代价越大——所以 7.3 的断言不是可选项。
2. **纵滑现在没有内容**。R2 只能靠单元测试验证（临时摆两个测试房间），
   真正生效要等第二章有「上楼」的关卡。在那之前它是「已实现的死代码」。
3. **房间正好一屏（1280×704），滑完刚好是完整新房间**，所以不会出现卷轴感。
   这是好事，但也意味着 R1/R2 的滑动距离恒等于 0.24s 走完一屏——没有快慢节奏变化。
4. **没有声音**。0.24s 的滑动配上 0 个音效，仍然是「画面在动、世界没反应」。
   这条与 A 方案的结论相同：滑动的可信度一半来自声音。
